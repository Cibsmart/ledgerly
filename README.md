# Ledgerly

A double-entry financial management application for internal business use — chart of accounts, journal entries, fiscal periods, and the four core financial statements.

Ledgerly is accounting software, so it is built around a small set of invariants that outrank convenience: entries balance or they do not persist, posted entries are never edited, statements are always derived, and money is never a float. Everything below exists to make those properties hard to break by accident.

## Getting started

Create an empty `ledgerly` database in PostgreSQL, then:

```bash
git clone <repository-url> ledgerly
cd ledgerly
composer setup
```

`composer setup` installs the Git hooks, installs PHP and Node dependencies, copies `.env.example` to `.env`, generates an application key, runs migrations, and builds frontend assets.

Then start the development environment:

```bash
composer dev
```

The app is served by [Laravel Herd](https://herd.laravel.com) at `http://ledgerly.test`. Do not run `artisan serve`.

## Accounting invariants

These are non-negotiable and are stated in full in `CLAUDE.md`:

1. **Debits equal credits, in the functional currency.** Enforced in the action layer before anything touches the database, and by a deferred database constraint. UI and request validation are conveniences, never the guarantee.
2. **Posted entries are immutable.** Corrections happen only through a reversing entry referencing the original. Enforced twice — in the write path, and by the models themselves.
3. **Statements are derived, never stored.** No column, cache, or table holds a statement figure as its own source of truth. If two reports can disagree, the design is wrong.
4. **Money is never a float.** See [Money](#money).
5. **Everything is attributable.** Every entry, posting, approval, and reversal records who and when.
6. **Closed periods are closed.** Once a period has `closed_at`, nothing posts into it.

## Architecture

Laravel 13 backend with an Inertia v3 + React 19 frontend, TypeScript, and Tailwind v4.

```
app/
├── Actions/   Single-purpose domain operations (PostEntry, ReverseEntry, ClosePeriod, …)
├── Casts/     Eloquent casts, including MoneyCast
├── Concerns/  Shared model and validation traits
├── Enums/     Backed enums for every status, type, role, and permission
├── Http/      Controllers, form requests, middleware
├── Models/    Eloquent models
└── Support/   Value objects and domain services (Money, report builders, …)

resources/js/pages/   Inertia page components
tests/Feature/        The bulk of the suite, organised by domain area
```

Business operations live in `app/Actions`, not in controllers — controllers validate, delegate to an action, and render. Each action is one class with one public `handle()` method.

All journal entry creation goes through `App\Actions\Ledger\PostEntry`; nothing else may build journal lines. Enforcement is deliberately layered: the action asserts balance before writing, and the line model throws from `booted()` on `updating` and `deleting`, so the invariant survives tinker, a seeder, or a future careless action.

Frontend route helpers are generated by [Wayfinder](https://github.com/laravel/wayfinder) — import from `@/actions/` or `@/routes/` rather than hardcoding URLs. Authentication is handled by Laravel Fortify, including two-factor and passkey support.

## Money and currency

**Money is never a float, never a decimal column, and never currency-less.** Every monetary column is a `bigInteger` of **integer minor units**, suffixed `_minor`, cast to the immutable `App\Support\Money` — which carries the `App\Support\Currency` those units are denominated in.

```php
$total  = $subtotal->add($tax)->subtract($discount);  // exact integer arithmetic
$shares = $total->allocate([70, 30]);                 // always re-sums to $total

$ngn = Money::fromMajor(100, Currency::of('USD'))
    ->convertTo(Currency::of('NGN'), '1650.25');      // explicit rate, half away from zero

Money::fromMajor(1, Currency::of('USD'))
    ->add(Money::fromMajor(1, Currency::of('NGN')));  // throws — a missing conversion
```

Three consequences worth knowing:

- **The test suite is trustworthy.** Tests run against SQLite `:memory:` for speed, and SQLite has no real `NUMERIC(15,2)` — it applies type affinity and can hold a decimal column as a float. Storing integers means the most important invariant in the system is verified on storage that behaves identically to production.
- **Cross-currency mistakes fail loudly.** Adding USD to NGN throws rather than producing a plausible wrong number. That exception always means a conversion is missing.
- **The frontend cannot drift.** `Money` serializes to `{minor, currency, formatted}`. React displays `formatted` and never computes.

Splits and percentage allocations use `Money::allocate()`, which applies largest-remainder rounding so the parts always re-sum to the original — no leaked or invented minor units. Scale is a property of each currency, not the application: JPY at scale 0 and KWD at scale 3 both work.

### Multi-currency

The books are kept in a single **functional currency** (`config/money.php`, NGN by default). Transactions may be in any configured currency, and every journal line carries three things: its transaction-currency amount, the exchange rate used, and the translated functional amount.

**Only the functional amounts balance.** A mixed-currency entry cannot net to zero in transaction-currency terms, so the trial balance — and the `expect($lines)->toBalance()` helper, which rejects non-functional amounts outright — sums `functional_amount_minor`.

Rates live in an `exchange_rates` table with effective dating, but a posted line never reads it again: the rate used is **snapshotted onto the line at post time**. Correcting a historical rate changes what future postings use and nothing about the past, which is what invariant 2 demands.

FX gain/loss is realized-only for now; period-end revaluation of open monetary balances is post-MVP.

## Quality checks

`composer test` runs Pint, Larastan, and Pest in sequence — the same gates CI enforces in `.github/workflows/tests.yml`.

Static analysis runs at **PHPStan level 7** with Larastan. Two non-default options in `phpstan.neon` are load-bearing:

- **`parseModelCastsMethod: true`** — models declare casts via a `casts()` method typed `array<string, string>`. Without this option Larastan reads that declared return type instead of the method body, and every enum and value-object cast — including `Money` — degrades to `string`, producing a large number of false positives.
- **`databaseMigrationsPath`** — lets Larastan infer column types from migrations.

There is deliberately **no PHPStan baseline**. The suite passes clean; keep it that way rather than suppressing new findings.

Two guardrails run as tests rather than as review conventions:

- `tests/Feature/Architecture/AuditCompletenessTest.php` fails when any action in `app/Actions` neither records an audit nor appears in a documented exemption list. New actions default to "must audit"; opting out is a reviewable edit with a stated reason.
- `expect($lines)->toBalance()` asserts a trial balance nets to zero. Every statement test uses it.

A pre-commit hook in `.githooks/` formats staged PHP with Pint and re-stages it, so commits record formatted code. It skips files with unstaged changes rather than committing work you left out. Install with `composer hooks`; bypass once with `git commit --no-verify`.

## Project status

Early. Phases 0–3 (foundation → chart of accounts → transactions → statements) are the MVP; the full roadmap is in `docs/plans/`. Phases 4–6 — investments, approval workflows, bank reconciliation — are not built, and should not be, even where the data model anticipates them.
